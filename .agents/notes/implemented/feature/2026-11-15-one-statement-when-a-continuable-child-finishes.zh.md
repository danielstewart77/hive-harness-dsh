# Agent Note: One statement when a continuable child finishes

Status: implemented

[English](2026-11-15-one-statement-when-a-continuable-child-finishes.md) | 中文

## 问题

一个完全照指令行事的可续背景子代，为一次结束让父代付出了两条消息。

[汇报义务](2026-08-06-continuable-child-report-obligation.md) 指示子代在结束前调用 `report` 交出自洽的结果，并把 `wakeup` 设为默认值，使该汇报能抵达已停泊的父代。随后 [由管理器负责的结算投递](2026-08-06-manager-owned-subagent-settlement-delivery.md) 让运行时无条件地交代子代的下场，并带上子代最后的助手内容。两者各自都是对的。合在一起，一个守规矩的子代产出：

```text
Background subagent <id> reported:
<the result>

Background subagent <id> finished and will do no further work unless you send it more.
Its closing message:
<the same result, in slightly different words>
```

在一个真实协调者的日志上实测：两条消息相隔九秒抵达，第二条重述了第一条。父代为同一个答案付了两次钱，还得自己推断出这两条消息描述的是同一次结束。这种重述不是措辞上的偶然。子代被告知汇报才是结果通道、而诸如 "done" 的收尾语毫无用处，于是一个汇报得好的子代会把答案写两遍——一遍写在要紧的地方，一遍写在退场路上。

这两条消息也无法排序。`subagent-report` 快照场景在出厂默认值下根本无法编写，因为汇报的唤醒与结算的唤醒以五五之比竞争：第二次究竟是延长了第一次的轮次，还是另开一轮。该场景固定 `reportDelivery: quiet`，纯粹是为了绕开它。

事后合并是不可能的。汇报的唤醒式投递会让父代在结算之前数秒就取走它，所以等到通知存在时，重复的那份早已被消费掉了。

## 决策

新增第三种 `reportDelivery` 模式 `settlement`：暂存汇报，并把它放进子代自己的结算通知里投递。它是默认值。

```text
Background subagent <id> finished and will do no further work unless you send it more.
Its report:
<the result>
```

一条消息，同时承载下场与结果，只有一次唤醒。

通知是用暂存的汇报**替换**收尾语重述，而不是追加在它之后。已经汇报过的子代，早已通过其自身指令所指定的结果通道说清了它产出了什么；在那之后再重述收尾语，正是本模式要消除的重复。多份暂存汇报各自带一个带标签的引导行——只有一份时是 `Its report:`，多份时是 `Its report 1 of 3:` 等等——这样父代能看出一份在哪里结束，以及子代给出它们的先后顺序。

`wakeup` 与 `quiet` 保持不变，连通知仍然承载收尾语这一点也不变。当父代必须在子代结束之前就对一份早期汇报作出反应时，部署保留的就是这两种模式；而把收尾语从它们当中拿掉，会让这样的部署失去子代始终没来得及汇报的那份最终答案的唯一副本。没有任何模式会产出一条重述另一条的消息。

### 投递仍然是无条件的，变的只是内容

[结算投递](2026-08-06-manager-owned-subagent-settlement-delivery.md) 否决了"仅在子代未汇报时才投递"，理由是它"会让面向父代的承诺变成有条件的"，并且彻底否决了把投递做成可配置项。两条结论依然成立，也都未被触碰：每个已宣告的子代在结算时都恰好发出一条通知，在所有模式下皆然，无论子代做了什么。本记录改变的是这一条通知承载哪些内容块。该条件不是关于某个管理器并不拥有的通道的簿记——它问的是管理器本身是否正为这个 epoch 暂存着内容，而那是它自己的状态，不是别人的。

因此承诺依然可以被陈述，而 `tool-subagent` 正陈述着它：通知承载下场与子代的结果——它汇报过的内容，或者它什么都没汇报时的最终助手消息。

### 来源信息

合并后的消息保留 `{ kind: 'subagent-settled', form: 'notice' }`。kind 命名的是这份交代的作者，而不是其中每个内容块的来源；而且通知本来就已经在管理器自己写的引导行之下引用子代了。`Its report:` 就是同一种构造。折叠起来的 `notice` 行仍然是管理器那一行下场陈述，所以子代的话绝不会以仿佛出自运行时之手的样子抵达 UI。

### 暂存绝不会比子代自己的工作活得更久

驻留 epoch 并不在空闲时结束。只要 Activation 还拥有存活的后代，`stateOf()` 就返回 `waiting`，所以一个先委派、随后安静下来的子代并没有在结算，也不会有通知到来。一直暂存到它整个子树结束，会把一个父代本已可以据之行动的结果搁死，而且无路可走：`interrupt()` 取消的是一个已经空闲的子代的当前轮次，并且不会向下级联。

所以暂存是在子代自身静止时释放，而不是在 Activation 结算时。当结算观察者看到一个静止却无法结算的子代时，它会把每份暂存汇报通过普通的唤醒式汇报路径冲出去，然后继续等待。于是一个会委派的子代退化成恰好是今天的两条消息——绝不会退化成无限期等待——而合并后的单条消息仍是常态，也就是所有不自行委派的子代。

在子代**已经**静止之后才被接受的汇报错过了那次观察，因此暂存它时会捅一下观察者,让它重新观察。只有服务 API 能抵达该状态；`report` 工具调用发生在轮次之内。

### 回执指向一条真实存在的消息

`report` 返回接受它的那条父代消息的 `MessageId`，[汇报工具](2026-07-30-continuable-subagent-report-tool.md) 也是这么说的。被暂存的汇报没有自己的消息，因此 Activation 在创建时就铸出结算通知的身份，并以该身份构建通知。于是子代的回执指向真正投递其汇报的那条消息，而不是一个悬空身份；并且一个 epoch 内暂存的每份汇报，都以承载它们全部的那一条消息的 id 得到回执。

### 子代被告知的内容

指引与工具描述按模式而异，因为决定是否再次调用的是子代，而诚实的答案因模式而不同。在 `settlement` 下，早期汇报换不来早期反应，所以邀请子代"每当某个局部发现改变了那个 agent 接下来该做什么时"就汇报，等于承诺了它得不到的东西；在那里成立的是：它汇报的任何内容都不会因为后来的汇报而被丢弃。在 `wakeup` 与 `quiet` 下，原本的邀请依然成立，也保持不变。

## 考虑过的替代方案

**在 `wakeup` 与 `quiet` 下也去掉收尾语。** 重复在那两种模式下同样真实，但在那里汇报已经作为自己的消息发出去了，所以移除重述移除的是内容本身，而不是它的一份副本：一个先汇报进展、继续工作、最后以一个始终未汇报的不同答案收尾的子代，会丢掉那个答案。那两种模式的存在就是为了替主动选择退出的部署保留今天的行为，所以它们保留它。

**通过把收尾语与已汇报内容作比较来去重。** 真实的重述是改写过的，而非逐字相同——实测的那一对没有共用任何一句话——所以精确匹配永远不会触发，而任何更宽松的做法都是在猜测语义。它还会让通知的内容取决于一个没人能核查的相似度阈值。

**把每份汇报都暂存到 Activation 结算。** 已在上文否决：一个会委派的子代会为它整个子树扣住一份已完成的结果，而 `interrupt()` 碰不到它。

**让子代按次选择模式。** 与[汇报工具](2026-07-30-continuable-subagent-report-tool.md)最初的否决一致：模型将掌握调度压力，而行为会按调用而异，而不是按部署而异。

**子代汇报过时就压制结算通知。** 这是那个有条件承诺，只是从另一侧抵达。一个无法依赖通知的父代反正还是会去轮询。

**限制一条通知承载的汇报数量。** 合并后的消息承载的内容，恰好就是父代本会以多条独立消息收到的那些；token 成本相同，减少的只是消息条数。设上限会悄悄丢弃子代已汇报的结果，那比它要修的重复更糟。

## 测试

- `packages/subagent/subagent/tests/continuation.spec.ts` 固定了合并行为：汇报后结束只有一条消息且没有独立的转达、收尾语被替换而非追加、多份汇报按接受顺序置于带编号的引导行之下、在 token 上限下仍承载暂存汇报因而被截断的子代不会被报成已完成、回执 id 等于所投递通知的 id、冷恢复跨 epoch 的隔离、静止子代仍拥有存活孙代时的冲出，以及通知无法投递时点明暂存汇报丢失的告警。既有的 `quiet` 测试另外固定了：独立调度的汇报不会让收尾语消失。
- `packages/subagent/tool-subagent-report/tests/tool-subagent-report.spec.ts` 固定了新的默认值、在该默认值下被接受的汇报既不入队也不启动父代请求却仍然抵达通知，以及面向子代的指引在每种模式下都如实说明投递时机。
- 组装后的 ACP `subagent-report` 场景现在跑在出厂默认值上，并端到端固定那一条合并消息。它的 `reportDelivery: quiet` 覆盖项已移除：只有一次唤醒时就没什么可竞争的了，而那正是该覆盖项当初要绕开的不确定性。

## 后果

- 一个守规矩的可续子代，每次结束让父代付出一条消息与一次唤醒，而不是各两次。扇出型部署每个子代省下一轮。
- `Activation` 携带 `heldReports` 与 `settlementMessageId`。汇报包"没有 Activation 状态、没有投递队列"的说法不再成立；[汇报工具记录](2026-07-30-continuable-subagent-report-tool.md) 记下了这处更正。
- `subagent-report` 场景不再需要配置覆盖项才能编写。`wakeup` 与 `quiet` 的覆盖保留在汇报包自己的测试里。
- `tool-subagent` 在其工具描述与提示段落中都承诺了通知的内容，所以两者随通知一起改变。每个组装转录中被固定的工具文本也随之移动。

### 已接受的风险

暂存汇报只存在于 Activation 上的进程内存中。暂存期间崩溃会丢掉它们且不留日志行，而立即投递的汇报此时早已持久化。子代自己的会话仍是恢复来源，正如它对其他每一种汇报投递失败而言已然如此。

自身世系正在关闭的父代会被注入而非唤醒，而它自己的处置会清掉未取走的通知。暂存汇报与之同命，而 `wakeup` 汇报通常早几秒就已抵达。那种情况下通知本就已经丢失；增量是它如今承载的结果。`wakeup` 是出口。

结果与结束现在一起传送，所以在取走那一条消息之前被取消的父代会同时丢掉两者，而此前结果位于它已取走的一条更早消息里。窗口是一个步边界。

一个先汇报、继续工作、最后以一个始终未汇报的不同答案收尾的子代，会让那个答案从通知中消失，因为通知一旦承载了汇报就会丢掉收尾语。子代收到的指令要求它每当结论改变时就再次汇报，而通知仍然承载真实的停止原因，所以父代绝不会被告知一个被截断的子代已经完成。
